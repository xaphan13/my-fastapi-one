# AionUI: глубокое исследование платформы

> **Срез исследования:** 25 июля 2026 года.  
> Название проекта в репозитории обычно пишется как **AionUi**, хотя на сайте используется **AionUI**.  
> Основные источники — GitHub/API, официальная wiki, сайт, релизы, issues/discussions, npm и Docker Hub. Независимых публикаций оказалось мало, поэтому это не рекламный пересказ, а анализ с указанием ограничений доказательной базы.

---

## 1. Краткий вывод

**AionUI — быстро развивающееся open-source desktop/WebUI-приложение для локальной работы с AI-агентами.**

Его ключевая идея — не просто чат с LLM, а единое рабочее пространство для:

- локальных и удалённых AI-моделей;
- встроенного агента;
- CLI-агентов Claude Code, Codex, Gemini CLI, Qwen Code и других;
- MCP-инструментов;
- команд агентов;
- фоновых и периодических задач;
- работы с файлами и рабочими директориями;
- генерации документов;
- удалённого доступа через WebUI и мессенджеры.

### Главная сильная сторона

AionUI особенно интересен как **локальный оркестратор разнородных AI-агентов**, а не как очередной интерфейс для одного API-провайдера.

### Главный недостаток

Проект очень активен, но пока имеет признаки **быстро меняющегося продукта с недостаточно зрелой публичной документацией по безопасности, приватности, телеметрии и эксплуатации**.

### Итоговая оценка

| Область | Оценка |
|---|---|
| Локальная работа с агентами | Очень сильная |
| Поддержка CLI-агентов | Очень сильная |
| MCP и интеграции | Сильная |
| Командный режим | Перспективный, но ещё развивающийся |
| WebUI и удалённая работа | Функционально сильная, требует hardening |
| Desktop UX | Сильный потенциал |
| Enterprise governance | Ограниченная публичная доказательная база |
| Безопасность | Необходим самостоятельный аудит |
| Стабильность | Активная разработка, но высокая скорость изменений |
| Лицензирование | Удобная Apache-2.0 |
| Независимая репутация | Пока ограниченная |

Для личного использования, экспериментов и локальной автоматизации AionUI выглядит перспективно. Для критически важных процессов и многопользовательского production-развёртывания его следует внедрять только через пилот, pinning версий и собственные проверки безопасности.

# 3. Архитектура

## 3.1. Общая схема

По официальным материалам AionUI состоит из:

1. **Electron-приложения**
   - main process;
   - preload;
   - renderer;
   - React/TypeScript/Vite-интерфейс.

2. **Локального AionCore backend**
   - отдельный исполняемый компонент;
   - отвечает за существенную часть агентской логики;
   - взаимодействует с моделями, MCP и CLI-агентами.

3. **SQLite**
   - локальное хранение данных;
   - история чатов;
   - конфигурация рабочих пространств;
   - состояния задач и агентов.

4. **Агентского слоя**
   - встроенный Aion Agent;
   - внешние CLI через ACP;
   - командные агенты;
   - scheduled tasks.

5. **WebUI**
   - desktop-вариант;
   - standalone HTTP-вариант;
   - удалённый доступ через браузер.

Архитектурная документация:

- [Development documentation](https://github.com/iOfficeAI/AionUi/blob/main/docs/contributing/development.md)
- [WebUI Configuration Guide](https://github.com/iOfficeAI/AionUi/wiki/WebUI-Configuration-Guide)

## 3.2. ACP и внешние CLI

AionUI использует **Agent Client Protocol** для подключения внешних агентов. Официальная wiki перечисляет:

- Claude Code;
- Codex;
- Qwen Code;
- Gemini CLI;

- Kiro;

- Augment;

Список в разные моменты документации немного различается.

Важная архитектурная особенность:

> AionUI не обязательно заменяет CLI-агент. Он выступает надстройкой, интерфейсом и оркестратором.

То есть авторизация, модели и собственные инструменты CLI могут оставаться под контролем соответствующего поставщика.

Это делает AionUI интересным для пользователей, которые уже используют несколько агентных инструментов, но не хотят переключаться между терминалом, браузером и отдельными приложениями.

## 4.2. Рабочие пространства и файлы

AionUI предоставляет:

- рабочие директории;
- историю разговоров;
- доступ агентов к файлам;
- предпросмотр файлов;
- управление разрешениями;
- вложения;
- выполнение операций в рамках workspace.

Это приближает AionUI к концепции Cowork/agent workspace, а не к обычному чат-клиенту.

Потенциальная ценность:

- анализ репозитория;
- генерация документов;
- обработка локальных данных;
- автоматизация повторяющихся рабочих процессов;
- запуск нескольких задач в одном проектном контексте.

Потенциальный риск:

- агент может читать и изменять файлы;
- MCP-инструменты могут расширять доступ;
- CLI-агенты могут иметь собственные полномочия;
- при включении автоматического подтверждения последствия действий становятся существенно серьёзнее.

Team mode позволяет использовать:

Эта часть активно менялась в релизах июля 2026 года. В issues одновременно встречаются сообщения о:

- преждевременном завершении командных запусков;
- восстановлении после сбоев;
- проблемах статусов;
- логике разрешений;
- retry и startup recovery.

Вывод:

> Team mode — одна из наиболее интересных функций AionUI, но её следует считать развивающейся, а не полностью зрелой enterprise-функцией.

## 4.4. Scheduled tasks

Поддерживаются:

- cron;
- interval;
- одноразовые задачи;
- фоновые задания;
- scheduled shortcuts;
- автоматизация 24/7.

Примеры сценариев:

- регулярный анализ папки;
- запуск отчёта;
- синхронизация;
- периодический мониторинг;
- автоматическая обработка документов;
- ночные агентские задачи.

Это важное отличие от большинства чат-интерфейсов.

Но scheduled tasks создают отдельный класс рисков:

- задача может запускаться без присутствия пользователя;
- изменённый prompt может привести к неожиданному действию;
- обновление агента или MCP может изменить поведение;
- ошибочная задача может повторяться;
- секреты могут быть доступны фоновому процессу.

# 5. Установка и развёртывание

## 5.1. Desktop

Доступны пакеты для:

- macOS:
  - Apple Silicon;
  - Intel;
- Windows;
- Linux:
  - DEB;
  - AppImage.

Также упоминается Homebrew-команда:

```bash
brew install aionui
```

Однако независимая проверка не обнаружила устойчиво подтверждённой официальной Homebrew formula на момент исследования. Поэтому Homebrew лучше перепроверять непосредственно перед установкой.

## 5.2. Заявленные требования

Официальная wiki:

- macOS 10.14+;
- Windows 10+;
- Linux Ubuntu 18.04+ или современные дистрибутивы;
- минимум 4 GB RAM;
- около 500 MB дискового пространства.

README в другом месте указывает более консервативные версии:

- macOS 10.15+;
- Ubuntu 18.04+;
- Debian 10+;
- Fedora 32+.

Это расхождение нужно учитывать. Для production лучше использовать требования README/release notes конкретной версии.

## 5.3. Standalone WebUI

Официальное руководство:

[WebUI Configuration Guide](https://github.com/iOfficeAI/AionUi/wiki/WebUI-Configuration-Guide)

Основные параметры:

- production-порт по умолчанию: `25808`;
- development-порт: `25809`;
- data directory:
  - `~/.aionui-web`;
  - для development — `~/.aionui-web-dev`;
- возможность переопределить `--port`;
- возможность переопределить `--data-dir`;
- режим `--remote`.

По умолчанию WebUI привязывается к localhost. В `--remote` он может слушать `0.0.0.0`.

### Механизмы защиты WebUI

По документации заявлены:

- случайно сгенерированный admin password;
- отображение пароля один раз;
- bcrypt;
- подписанные непрозрачные cookies;
- срок действия cookie около 24 часов;
- ограничение попыток входа;
- CSRF-защита.

Одновременно документация рекомендует:

- VPN;
- firewall;
- Tailscale;
- не выставлять WebUI напрямую в интернет.

### Что не подтверждено публично

В доступной документации не удалось найти достаточную детализацию по:

- TLS termination;
- полноценному reverse-proxy hardening;
- ротации секретов;
- audit logs;
- multi-tenant isolation;
- шифрованию локальной базы;
- session invalidation;
- централизованному управлению пользователями;
- SSO/OAuth/LDAP;
- резервному копированию;
- формальной модели угроз.

> AionUI — продукт с высокой скоростью изменений, где одновременно развиваются core, desktop, WebUI, команды, Docker и интеграции с внешними агентами.

Это требует:

- фиксировать версии;
- тестировать обновления;
- иметь rollback;
- не обновлять production автоматически;
- хранить резервные копии workspace и конфигурации.

Таким образом, основная доказательная база AionUI сегодня — это:

1. собственный репозиторий;
2. официальный сайт;
3. официальная wiki;
4. GitHub issues/discussions;
5. релизы;
6. пакеты и образы экосистемы.

Это означает, что маркетинговые заявления следует проверять самостоятельно.

# 10. Приватность и движение данных

## 10.1. Официальное заявление

В FAQ и README утверждается:

- выполнение локально;
- локальная SQLite;
- данные не загружаются на сервер AionUI;
- прямое взаимодействие с выбранными API-провайдерами.

Это полезная архитектурная характеристика, но это всё ещё **заявление разработчиков**, а не результат независимого аудита.

## 10.2. Реальная поверхность передачи данных

Даже при локальном размещении возможна передача данных:

- выбранному LLM-провайдеру;
- web search provider;
- MCP-серверам;
- внешнему CLI;
- Telegram/Lark/DingTalk/WeChat;
- remote WebUI;
- удалённым API, подключённым через OpenAI-compatible endpoint.

Поэтому «локальный» не означает «данные никогда не покидают компьютер».

## 10.3. Что не было достаточно документировано

Не удалось найти полноценную публичную privacy policy с деталями по:

- telemetry;
- crash reporting;
- analytics;
- retention;
- удалению данных;
- резервным копиям;
- encryption at rest;
- хранению API keys;
- opt-out;
- DNS/network endpoints;
- содержимому диагностических логов.

Важно:

> Отсутствие документации не доказывает наличие телеметрии. Но до аудита это остаётся неизвестностью.

# 11. Безопасность

## 11.1. Основные классы угроз

AionUI объединяет локальные файлы, агентов, внешние API, MCP и удалённый доступ. Возможные риски:

### 1. Prompt injection

Источники:

- загруженные файлы;
- веб-страницы;
- репозитории;
- документы;
- сообщения из мессенджеров;
- MCP-ответы.

Агент может быть убеждён выполнить не предусмотренную пользователем операцию.

### 2. Чрезмерные права агента

Агент может:

- читать файлы;
- создавать и изменять файлы;
- запускать CLI;
- вызывать MCP-инструменты;
- взаимодействовать с сетью;
- выполнять фоновые задачи.

### 3. MCP supply-chain risk

Сторонний MCP-сервер способен:

- видеть передаваемые данные;
- вызывать внешние сервисы;
- получать секреты при неправильной конфигурации;
- выполнять операции с широкими полномочиями.

### 4. Риск unattended automation

Cron и interval-задачи могут продолжать работу без пользователя.

### 5. WebUI exposure

При `--remote` приложение может быть доступно по сети. Риски:

- кража admin password;
- ошибки reverse proxy;
- отсутствие TLS;
- неправильная настройка firewall;
- компрометация cookie;
- доступ к рабочим файлам и агентским действиям.

### 6. CLI-agent trust boundary

Каждый внешний CLI может иметь собственную:

- авторизацию;
- модель;
- систему инструментов;
- права;
- поведение;
- обновления.

AionUI добавляет единый интерфейс, но не отменяет риски самих CLI.

### 7. Updater и binary supply chain

Desktop-версии используют обновляемые бинарные компоненты. Нужно проверять:

- checksum;
- provenance;
- подписи;
- release commit;
- источник обновления;
- состав бинарей.

## 11.2. Важный security-related issue

Обнаружен issue [#3077](https://github.com/iOfficeAI/AionUi/issues/3077), опубликованный 28 мая 2026 года.

Автор утверждает, что Windows-обновление версии v2.1.4 доставило `aioncore.exe`, который был обнаружен как:

> `Trojan-Spy.Win32.Stealer.fsbv`

В issue приводится MD5, но не было найдено достаточных независимых материалов:

- полноценного образца;
- подробных логов;
- воспроизводимого анализа;
- подтверждения независимой лабораторией;
- однозначной реакции maintainers.

Issue остаётся открытым/неразрешённым на момент проверки.

Корректный вывод:

> Это неподтверждённое обвинение, а не доказательство того, что AionUI содержит вредоносный код.

Но для Windows-окружения это достаточно серьёзный сигнал, чтобы:

- не устанавливать бинарь без проверки;
- использовать антивирусный анализ;
- сравнивать hashes;
- проверять подписи;
- скачивать только с официального релиза;
- тестировать в изолированной VM;
- рассмотреть сборку из исходников.

## 11.3. YOLO / Full-Auto режимы

В проекте присутствуют режимы, которые автоматически подтверждают действия агента или обходят обычные запросы разрешений.

Это удобно для автоматизации, но опасно при:

- доступе к production workspace;
- наличии секретов;
- внешних MCP;
- удалённом WebUI;
- scheduled tasks;
- непроверенных prompts;
- обработке непроверенных файлов.

Для первоначального внедрения рекомендуется:

- отключить YOLO;
- отключить unattended schedules;
- использовать отдельного пользователя ОС;
- создать отдельную рабочую директорию;
- ограничить MCP;
- не использовать production credentials.

# 13. Сравнение с альтернативами

## 13.1. Open WebUI

Репозиторий: [open-webui/open-webui](https://github.com/open-webui/open-webui)

### Сильные стороны Open WebUI

- web-first и self-hosted;
- Docker/Kubernetes/Helm;
- Ollama и OpenAI APIs;
- RAG;
- plugins;
- MCP;
- RBAC;
- groups;
- LDAP/OAuth;
- trusted headers;
- SCIM;
- более выраженная multi-user ориентация.

### Слабые стороны относительно AionUI

- менее сфокусирован на heterogeneous CLI-agent orchestration;
- desktop-native опыт не является центральным сценарием;
- расширения и tools также создают значительную поверхность атаки;
- лицензирование Open WebUI требует внимательного чтения текущих условий.

На момент исследования:

- около 146,7 тыс. stars;
- около 21,3 тыс. forks.

## 13.2. LibreChat

Репозиторий: [danny-avila/LibreChat](https://github.com/danny-avila/LibreChat)

### Преимущества

- MIT;
- OAuth2;
- LDAP;
- email auth;
- RBAC;
- groups;
- Docker/Helm;
- Redis/S3;
- MCP;
- RAG;
- artifacts;
- code execution sandbox.

### Важный плюс

У LibreChat есть публичная security-страница и advisories:

[LibreChat Security](https://github.com/danny-avila/LibreChat/security)

Там опубликованы проблемы, включая:

- stored XSS;
- SSRF;
- MCP OAuth validation;
- file traversal;
- exposure MCP secrets;
- URL injection;
- IDOR;
- rate limiting issues.

Это не означает, что LibreChat безопасен по умолчанию. Но прозрачный disclosure-процесс — позитивный признак зрелости.

## 13.3. LobeChat

Репозиторий: [lobehub/lobe-chat](https://github.com/lobehub/lobe-chat)

### Преимущества

- большое agent ecosystem;
- MCP;
- plugins;
- memory;
- schedules;
- gateways;
- web deployment;
- Docker/Vercel/self-hosting.

### Ограничения

- лицензия LobeHub Community License не равна простой MIT/Apache-2.0;
- нужно внимательно проверять ограничения;
- публичная документация по data-flow и retention менее очевидна;
- desktop-first workflow AionUI выражен сильнее.

## 13.4. Cherry Studio

Репозиторий: [CherryHQ/cherry-studio](https://github.com/CherryHQ/cherry-studio)

### Преимущества

- desktop-клиент;
- Windows/macOS/Linux;
- локальные модели через Ollama/LM Studio;
- MCP;
- документы;
- WebDAV;
- мульти-модельная работа.

### Отличие от AionUI

Cherry Studio ближе к универсальному desktop AI-клиенту. AionUI сильнее сфокусирован на:

- агентах;
- CLI-интеграции;
- scheduled tasks;
- командном выполнении;
- Cowork/workspace-модели.

Cherry Studio распространяется в рамках AGPL-3.0 Community Edition и коммерческих условий, что принципиально отличается от Apache-2.0 AionUI.

# 17. Что выглядит особенно перспективно

1. **ACP-агрегация**  
   Возможность работать с несколькими CLI-агентами из одного интерфейса — наиболее заметная дифференциация.

2. **Локальная Cowork-модель**  
   Workspace, файлы, разрешения и agent actions объединены в единый workflow.

3. **Команды агентов**  
   Team mode может быть полезен для параллельного анализа и выполнения задач.

4. **Фоновые задачи**  
   Cron и interval превращают чат-интерфейс в automation platform.

5. **MCP synchronization**  
   Удобно централизованно подключать инструменты к нескольким агентам.

6. **Документы**  
   PPTX/XLSX/DOCX/PDF расширяют применение за пределы программирования.

7. **Desktop + WebUI + messaging channels**  
   Один и тот же агентский workflow может быть доступен из разных каналов.

# 18. Что вызывает наибольшие вопросы

1. Недостаточная публичная детализация privacy/telemetry.

# 19. Финальный вердикт

AionUI — **не просто чат-клиент**, а попытка создать локальную операционную среду для AI-агентов:

- desktop-first;
- с CLI-агентами;
- MCP;
- workspace;
- командным выполнением;
- расписаниями;
- удалёнными каналами;
- документами;
- WebUI.

По функциональной широте и скорости развития проект выглядит очень сильным. Особенно он подходит пользователям, которые:

- используют Claude Code, Codex, Gemini CLI или другие CLI-агенты;
- хотят работать с несколькими провайдерами;
- нуждаются в локальном workspace;
- хотят запускать автоматические задачи;
- предпочитают open-source и self-hosting;
- не хотят собирать такую систему вручную.

Однако AionUI пока следует воспринимать как:

> **быстро развивающуюся агентскую платформу с высоким потенциалом, но ещё не как доказанно зрелую enterprise-систему с полной security/compliance-документацией.**

### Рекомендация

Для личного использования:

- попробовать можно;
- лучше использовать отдельный workspace;
- фиксировать версии;
- отключить автоматические разрешения;
- не подключать чувствительные секреты.

Для команды:

- запускать через пилот;
- ограничить MCP и WebUI;
- внедрить backup и rollback;
- тестировать каждое обновление.

Для production/enterprise:

- не использовать без собственного аудита;
- не выставлять WebUI напрямую в интернет;
- применять VPN или zero-trust;
- проверять бинарные релизы;
- потребовать от проекта более подробные сведения о telemetry, security process, session isolation и secret storage.

**Мой общий вывод:** AionUI стоит изучать и пилотировать, особенно если главная задача — объединить множество AI-агентов и CLI-инструментов в локальном рабочем пространстве. Но его текущая зрелость больше соответствует категории **advanced open-source beta / rapidly evolving platform**, чем полностью сформированной корпоративной инфраструктуре.
