# 01. Две половины одного приложения: кто где исполняется

> Цикл «FastAPI + React». Предыдущая: [README](README.md) · Следующая: [02. Каркас бэкенда](02-fastapi-backend.md)

## 1. Главная картинка, которую нужно держать в голове

Самое частое непонимание новичка: «React-приложение крутится на сервере, и сервер
его рендерит». Это не так в 90% современных проектов. Правильная картина:

```
┌────────────────────────── БРАУЗЕР ПОЛЬЗОВАТЕЛЯ ──────────────────────────┐
│                                                                          │
│   index.html  +  bundle.js  +  bundle.css   ← скачаны один раз           │
│                                                                          │
│   React исполняется ЗДЕСЬ:                                               │
│   • рисует UI (виртуальный DOM → реальный DOM)                           │
│   • роутинг по страницам (React Router, без перезагрузок)                │
│   • состояние интерфейса (форма, модалка, тема, авторизация)             │
│   • fetch('/api/...') за данными                                         │
│                                                                          │
└───────────────▲───────────────────────────────▲──────────────────────────┘
                │ статика: JS/CSS/HTML          │ JSON: /api/...
                │                               │
┌───────────────┴───────────────────────────────┴──────────────────────────┐
│                         СЕРВЕР: FastAPI (Python)                          │
│                                                                           │
│   • раздаёт собранную статику фронтенда (mount + SPA fallback)            │
│   • JSON API: валидация, бизнес-логика, БД, сессии, файлы                 │
│   • SQLAlchemy async → PostgreSQL / SQLite                                │
│                                                                           │
└───────────────────────────────────────────────────────────────────────────┘
```

**Вывод 1.** React — это библиотека для *браузера*. Node/Vite нужны только чтобы
*подготовить* JS-файлы (скрипты, сборка). После `npm run build` Node можно
выключить — сайт продолжит работать, потому что FastAPI просто раздаёт готовые файлы.

**Вывод 2.** «Фронтенд-сервер» — это не условие работы сайта, а условие *удобной
разработки* (HMR, прокси, типизация). В проде его нет.

## 2. Единственная связь: контракт JSON API

Две половины приложения не знают друг о друге ничего, кроме **формата обмена**.
В этом проекте контракт выглядит так (реальный эндпоинт блога):

```
GET /api/blog/articles/{art_id}
  → 200 {"article": {"id": 7, "title": "...", "author": "Max",
                     "lang": "Rust", "section": "backend",
                     "content": "<h1>...</h1> ..."}}     ← HTML уже отрендерен сервером
  → 404 {"detail": "Article not found"}
```

Из этого контракта фронтенд-разработчик пишет TypeScript-тип и функцию запроса
(`frontend/src/api/blog.ts` — реальный код):

```typescript
// GET /api/blog/articles/{art_id} — одна статья с готовым HTML-контентом.
export function getArticle(artId: number | string): Promise<{ article: Article }> {
  return getJson<{ article: Article }>(`/api/blog/articles/${artId}`);
}
```

…а бэкенд-разработчик — pydantic-схему и обработчик. **Контракт — это граница
команд и граница понимания.** Пока он зафиксирован (а FastAPI бесплатно
документирует его через OpenAPI/Swagger на `/docs`), обе половины можно писать
параллельно и даже разными людьми.

## 3. Почему именно SPA + JSON API (а не серверные шаблоны)

Современный подход «по умолчанию» для интерактивных приложений:

| Требование | Как его закрывает SPA + API |
|---|---|
| Интерактив без перезагрузок | React Router + локальное состояние |
| Переиспользование API | Тот же `/api/...` отдаёт данные мобильному приложению, скриптам, интеграциям |
| Разделение труда | Фронтендер правит `frontend/src`, бэкендер — Python; конфликтуют только в контракте |
| Скорость отклика UI | Данные — маленький JSON; разметка строится на клиенте |
| Разные клиенты | Браузер — один клиент из многих |

Когда это *не* лучший выбор — см. [статью 07](07-alternatives.md): для
SEO-критичных контентных сайтов лучше SSR, для маленьких интерактивных вставок —
Jinja2 + htmx.

## 4. Три режима жизни связки

Один и тот же код существует в трёх режимах. Их важно не путать:

### Режим разработки (два процесса)

```bash
cd fastapi-application && ../.venv/bin/uvicorn main:main_app --port 8000   # API
cd frontend && npm run dev                                                 # Vite :5173
```

Браузер ходит на `:5173`. Vite отдаёт исходники «как есть» с мгновенным
обновлением при сохранении (HMR), а запросы `/api` и `/static` незаметно
проксирует на FastAPI (`frontend/vite.config.ts` — реальный код):

```typescript
server: {
  port: 5173,
  proxy: {
    "/api":    { target: "http://localhost:8000", changeOrigin: true },
    "/static": { target: "http://localhost:8000", changeOrigin: true },
  },
},
```

### Режим эксплуатации (один процесс)

```bash
cd frontend && npm run build        # → frontend/dist/ (index.html + assets/)
cd fastapi-application && ../.venv/bin/uvicorn main:main_app --port 8000
```

FastAPI монтирует `dist/assets` и отдаёт `index.html` на любой «не-API» путь.
Один порт, один процесс, никакого Node.

### Режим CI/проверки

```bash
cd fastapi-application && ../.venv/bin/python -c "from main import main_app; print(len(main_app.routes))"
curl -s http://127.0.0.1:8000/api/blog/articles | head -c 200
```

## 5. Типичная ошибка, которая стоит часа отладки

**Правки в `frontend/src/` не видны на `:8000` до пересборки.** Браузер получает
старый бандл из `dist/`. Отсюда рабочее правило:

> Разрабатываешь UI — работай через `:5173` (`npm run dev`).
> Закончил — сделай контрольный `npm run build` и проверь на `:8000`.
