ADV-005: Регистрация — проверка уникальности
============================================

Схема RegisterIn (из openapi.json):
  username, email, password, confirm_password — все required string.

Кейс U1: дубль USERNAME (разные email)
  POST register { username="dup_X", email="a@ex.com", ... } -> 200 OK
  POST register { username="dup_X", email="b@ex.com", ... } -> 422
    {"errors":{"username":["That username is taken. Please choose a different one."]}}
  -> PASS (валидация на username работает).

Кейс U2: дубль EMAIL (разные username)
  POST { email="dup_X@ex.com", username="uA" } -> 200 OK
  POST { email="dup_X@ex.com", username="uB" } -> 422
    {"errors":{"email":["That email is taken. Please choose a different one."]}}
  -> PASS.

Кейс U3: дубль EMAIL с пробелами по краям
  POST { email="  dup_X@ex.com  " } -> 422 "email taken"
  -> PASS: Pydantic EmailStr .strip()'ит, и валидация срабатывает.

Кейс U4 (ВНИМАНИЕ): дубль EMAIL в UPPERCASE
  POST { email="DUP_X@EXAMPLE.COM" } -> 200 OK (!!!)
  POST { email="dup_x@example.com" } -> 200 OK (уже существует)
  -> FAIL: email НЕ приводится к lowercase, и считается уникальным.
     Это создаёт две разные учётки для одного и того же email-адреса.
     Если пользователь потом захочет "reset password" — какой из них получит
     письмо? Какой логин будет "каноническим"? Путаница и потенциальный
     угон через подбор регистра.

Suggested severity: MEDIUM
  (не критично для безопасности, но логический баг в нормализации;
   пользователь может создать себе несколько аккаунтов на один email,
   что ломает модель "email = уникальный идентификатор")
