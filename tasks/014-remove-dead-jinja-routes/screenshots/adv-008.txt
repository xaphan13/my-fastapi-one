ADV-008: Account POST — валидация username и CSRF-механика
=========================================================

ВАЖНОЕ наблюдение по CSRF: для /api/blog/account POST CSRF проверяется через
**тело формы** (multipart/form-data, поле csrf_token), а не через заголовок
X-CSRF-Token. Заголовок X-CSRF-Token вернул 403 в обоих случаях:
  - только заголовок: 403
  - только csrf_token в форме: 200 OK
  - оба: 200 OK
Login/register/logout — CSRF проверяется через ЗАГОЛОВОК X-CSRF-Token.

Это асимметрия: для разных маршрутов — разные правила. Документация должна
отражать это явно. Не критично, но потенциально сбивает с толку разработчиков.

Валидация username (RegisterIn / AccountIn):
  Только длина 2-20 символов. Никаких других ограничений.

Кейсы (multipart POST с правильным csrf_token):
  [422]  XSS script ("><script>alert(1)</script>) — длина >20, ОТКЛОНЁН
  [422]  JSON-like ({"$ne":null}) — длина >20, ОТКЛОНЁН
  [200]  SQL injection (admin' OR '1'='1) — ПРИНЯТ (17 символов) !!!
  [422]  SQL injection 2 (DROP TABLE) — длина >20, ОТКЛОНЁН
  [200]  emoji (admin😈hacker) — ПРИНЯТ
  [200]  newline (admin\nhacker) — ПРИНЯТ
  [200]  tab (admin\thacker) — ПРИНЯТ
  [422]  CRLF (admin\r\nX-Injected) — длина >20, ОТКЛОНЁН
  [200]  null byte (admin\x00hacker) — ПРИНЯТ

Сохранённый username возвращается как JSON. React (или любой нормальный фронт)
это экранирует, XSS не происходит. Но:
  - SQL-инъекция в виде строки безвредна (SQLAlchemy параметризует запросы).
  - null byte, newline, tab — могут сломать терминальный вывод (logs).
  - Emoji — допустимы, обычно это не баг.
  - homoglyph (cyrillic 'a' вместо latin 'a') — позволит зарегистрировать
    "admin" визуально неотличимый от настоящего.

Suggested severity: LOW (визуальная обфускация, не дыра в безопасности)
